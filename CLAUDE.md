# Lightroom MCP AI (`@pired/lightroom-mcp`)

Published on npm as `@pired/lightroom-mcp` (bin: `pired-lightroom-mcp`). MCP server bridging Claude / DeepSeek / any MCP client to Adobe Lightroom Classic, with hybrid AI Denoise, spot removal, local + AI + range masks, tone curves, Auto commands, scoped resets, process version, snapshots, JPEG previews (inline images), selection & navigation, batch IPTC and catalog inventory. Fork of Automaat/lightroom-mcp (56 tools).

## Layout

- `server/` — TypeScript MCP server (ESM, NodeNext). Stdio transport for Claude + raw TCP client to plugin sockets.
- `plugin/LightroomMCP.lrplugin/` — Lua plugin loaded by Lightroom Classic.
- `skills/photo-edit-advisor/` — agent skill (dust detection, shadow-lift headroom). Python, numpy + pillow only, NOT scipy. Lives outside `server/`, so it is not in the npm tarball. `mise run skill:test` discovers skills by glob; the task fails if no skill has a `tests/` directory, because the previous hardcoded path pointed at a directory that never existed and CI stayed green on it. Its `evals/` are a MANUAL gate, not CI: the reference photos live on the photographer's disk and are re-exported per run (`python scripts/run_evals.py <exportdir>`). Two cases are opposite states of one photo and cannot both be exported at once — read the `requires` notes before concluding the code broke.
- `manual-test.mjs` — direct TCP probe (bypasses MCP) for validating plugin dispatch.
- `server/scripts/sync-bundle.mjs` — runs after `tsc` as part of `npm run build`; copies the plugin + DeepSeek harness + client configs into `server/dist/` so the npm tarball (`files: ["dist", ...]`) is self-contained. Keep it in the build, or `install-plugin` breaks for npm users.

## AI additions — design constraints (read before touching them)

- `ai_denoise` (`HandlerAI.lua`): Adobe exposes no SDK API for AI Denoise, so the handler selects the photo via `catalog:setSelectedPhotos` (OUTSIDE any catalog gate — it yields), runs a temp PowerShell script through `LrTasks.execute` that AppActivate + SendKeys opens Photo > Enhance and confirms it, then polls the photo's folder for a brand-new DNG (via `LrFileUtils.directoryContents` snapshot diff) and waits for the catalog to register it. `LrTasks.execute` does not capture stdout, so the PS script reports through a result file. Every key/timing is caller-overridable (`native_automation`). If the native path cannot be verified, apply ISO-aware manual sliders and report `method: "manual_fallback"`. Keep the honest-reporting contract: never claim native success without the DNG.
- `HandlerSpots.lua`: RetouchInfo is a LIST of flat strings `(x,y),(heal|clone),(srcX,srcY),(radius),(f),(o),(flags)` (XMP Seq of strings; the SDK returns a table). Never rewrite existing entries; verify writes by reading back (formats are undocumented by Adobe — the read-back is the only truth).
- `HandlerLocalAdjustments.lua`: appends corrections to `MaskGroupBasedCorrections` (SDK 11+). Local*2012 sliders are fractions -1..1 except LocalExposure2012 (EV). Linear masks are defined by Zero/Full endpoints; radial by Top/Left/Bottom/Right + Feather + Flipped. When the photo already has corrections, clone one as a template so per-version fields survive — **and clone its MASK entry too**: the fields LrC requires (`Version`, `MaskBlendMode`, `Midpoint`, `Roundness`) live on the mask, not the correction wrapper. Building a fresh mask entry from geometry alone made LrC 15.4 accept the correction and silently discard its mask, leaving `CorrectionMasks` empty — an adjustment with no geometry that also stopped the photo rendering previews. Regenerate `CorrectionID`/`CorrectionSyncID`/`MaskID`/`MaskSyncID` on the clone; inheriting them showed two corrections under one name in the Masks panel. **Verify by counting MASKS, not corrections**: the correction count grows even when the mask was thrown away, which is exactly how this reported `applied: true` on a no-op.
- `set_flags` (`HandlerOrganization.lua`): LrSelection commands act on the UI selection (grid: all selected; loupe: active only) — select first, command, then verify per photo via `pickStatus` (1 pick / -1 reject / 0 none) and retry singly on misses.
- `set_white_balance` (`HandlerDevelop.lua`): uses `applyDevelopSettings(settings, name, optFlattenAutoNow)` — the 3rd param resolves "Auto" synchronously on SDK 13+.
- Watermarking: `HandlerWatermark.listWatermarks` scans `<appPrefs>/Watermark Presets/*.watermark`; `HandlerExport` sets `watermarking = { watermarkEnabled, watermarkSelection }` in export settings (key not officially documented — best effort, documented as such in the README).
- Windows-first: the native denoise automation is Windows SendKeys; on other platforms `sendNativeDenoiseKeys` reports unavailable and the hybrid falls back.
- `HandlerAIMasks.lua` (v2.0): AI masks use the official `LrDevelopController.createNewMask("aiSelection", subtype)` API (LrC 12.4+). These are DOT calls (no implicit self) — mock signatures in specs must NOT take a leading `_`. The controller drives the running Develop module: `LrApplicationView.switchToModule("develop")` once per call, `catalog:setSelectedPhotos` per photo, both OUTSIDE any catalog gate. Temperature/Tint are deliberately absent from mask adjustments (mask-context units are undocumented; global overwrite risk) — local color goes through `add_local_adjustment` instead. `remove_mask` verifies via before/after `getAllMasks()` count (entry shapes vary per LrC version); a non-matching id reports `verified=false`, not an error.
- `set_tone_curve` / `get_tone_curve` (`HandlerDevelop.lua`, v2.0): Lightroom stores point curves as flat `{x1,y1,x2,y2,...}` arrays in 0-255 space (`ToneCurvePV2012` + Red/Green/Blue). Endpoints (0,0)/(255,255) are auto-inserted and reported via `endpoints_added`; x must be strictly increasing. Always set `ToneCurveName2012` alongside ("Custom" for user points, the matching UI name for presets) and verify by reading the curve back.
- `apply_auto` (`HandlerDevelop.lua`, v2.0): `LrDevelopController.setAutoTone()` / `setAutoWhiteBalance()` called BARE through `runDevelopCommand` — never inside `withWriteAccessDo` (see the LrDevelopController rule below). Per photo: select (outside gates) → snapshot settings → commands → settle sleep → read-back diff of the main sliders. "No slider changes" is only reported when the commands actually RAN; if one failed, the note says so and points at `tone_error` / `white_balance_error` instead of offering the benign "may already be optimal" explanation.
- `set_color_label` / `create_virtual_copies` / `create_smart_collection` (`HandlerOrganization.lua`, v2.0): labels use `setRawMetadata('label', ...)` with capitalized color names, nil clears, case-insensitive read-back (custom label sets). Virtual copies call `photo:createVirtualCopy()` inside a write gate and return the new ids. Smart collections take the SAME searchDesc shape as `findPhotos` (`{ combine = "intersect"|"union", {criteria=, operation=, value=, value2=} }`) — reuse, don't invent a format.
- `get_photo_preview` (`HandlerPreview.lua`, v3.0): `photo:requestJpegThumbnail(size, size, callback)` is ASYNC — poll a done-flag with `LrTasks.sleep`, both render and sleep OUTSIDE any catalog gate. The JPEG is written under `~/.config/lightroom-mcp/previews/` (retention: newest 60, pruned best-effort) and the result carries `image_attached_by_server: true`; `server/src/tool-handler.ts` reads the file back and attaches it as an MCP image content block (cap 5MB, honest warning fallback). Text-only clients still get `file_path` from the JSON text. **The callback fires more than once per request** — Lightroom delivers progressively better renditions and can interleave a transient `errorMsg` — so the handler keeps the LAST complete JPEG (validated by SOI/EOI magic bytes), treats an error as terminal only if nothing valid ever arrives, and settles for `RENDER_SETTLE_S` after the first good one. Treating the first callback as final is what made this tool return a blank image and fail with "error loading thumb" on photos that render fine in the UI. `renditions_received` reports what actually arrived; an implausible byte count for the requested size raises `warning` rather than being trusted silently.
- `get_develop_settings` (`HandlerDevelop.lua`, v3.0): `photo:getDevelopSettings()` inside a read gate; per-key `cloneSerializable(value, 0, {})` — unsupported keys are SKIPPED and reported in `skipped_fields`, never fail the whole read (passing depth>0 to cloneSerializable rejects immediately; its hard cap is `depth >= 6`).
- `reset_develop` / `set_process_version` / `create_snapshot` (v3.0): LrDevelopController reset surface (`resetAllDevelopAdjustments`, `resetCrop`, …, `resetToDefault(key)`) — DOT calls, BARE (no write gate), after the standard switch-to-Develop-and-select dance. `createDevelopSnapshot` is the exception: it is a photo method, so it stays inside `withWriteAccessDo`. `setProcessVersion` accepts `"Version 1".."Version 6"` and verifies via `getProcessVersion()` read-back. `createDevelopSnapshot` is create-only (SDK exposes no list/apply) — say so in the result note instead of faking verification.
- **LrDevelopController commands are NEVER wrapped in `catalog:withWriteAccessDo`** (`runDevelopCommand` in `HandlerDevelop.lua`). They drive the running Develop module and open their own catalog transaction, so nesting one inside our own write gate makes Lightroom reject it every single time with "blocked by another write access call" — deterministic, not intermittent, not photo-dependent. This shipped three separate times (`apply_auto` twice, `set_process_version` once) because the spec mock was a bare passthrough. `spec_helper` now throws on both nested gates and controller commands called inside one, so the mistake fails CI. Genuine catalog writes (`photo:applyDevelopSettings`, `photo:createVirtualCopy`, `catalog:removePhoto`, …) still belong INSIDE the gate.
- `select_photos` / `navigate_photo` (`HandlerSelection.lua`, v3.0): the PUBLIC selection tool (the old `set_selection` stays test-only, reachable solely through the raw TCP probe). LrSelection mode commands (`selectAll`/`selectNone`/`selectInverse`/`deselectOthers`/`nextPhoto`/`previousPhoto`) are dot-style, no gate. A Lua gotcha bit us here: `{...}[key]` is NOT a valid Lua 5.1 expression — assign the table to a local first (lupa's 5.4 runtime accepts it, Lightroom's 5.1 does not).
- `batch_metadata` / `get_photo_status` / `rotate_photo` / `remove_from_catalog` (v3.0): whitelisted IPTC keys with per-photo read-back verification; status maps `pickStatus` 1/-1/0 → pick/reject/none; `removePhoto` is gated behind `confirm == true` in BOTH the contract (`enum: [true]`) and the handler, and verifies via re-resolution afterwards.
- `HandlerCatalog.lua` (v3.0): `getFolders`/`getKeywords` are plain catalog reads (inside read gates, like `getChildCollections` — they do NOT yield). `setViewFilter` is called BARE (no gate) matching lightroom-cli's tested implementation, pcall-wrapped; `getCurrentViewFilter` reads inside a read gate with a bare-call fallback.
- `Corrections.lua` + `list_masks` / `remove_mask` (v3.2): the mask inventory reads and writes **`MaskGroupBasedCorrections` directly**, never `LrDevelopController.getAllMasks()`. getAllMasks() only reflects the photo loaded in the Develop module and does NOT see corrections written through `applyDevelopSettings`: measured on a photo where `read_local_adjustments` reported one mask, getAllMasks() reported zero and both removal paths (`deleteMask` by id, `resetMasking` for remove_all) silently removed nothing — so anything `add_local_adjustment` created could not be deleted through the server at all. When the two sources disagree, the stored table is right. Consequences to preserve: removal drops a correction left with no masks (an adjustment with no geometry is the shape that stopped a photo rendering previews), an id that matches nothing returns `success: false` rather than a hollow success, and neither tool switches modules or touches the selection.
- `add_range_mask` / `adjustment_preset` / `remove_all` (v3.0): `createNewMask("rangeMask", "luminance"|"color"|"depth")` shares `runMaskCreationBatch` with the AI masks; the SDK cannot set range bounds or sample points — the tool description AND the result `note` both say so (honest limitation, don't remove it). Mask adjustment presets (darken_sky…enhance_landscape) come from lightroom-cli's presets.py minus `warm-skin` (Temp/Tint, see the ADJUSTMENTS note). `remove_mask` with `remove_all=true` + `confirm=true` calls `resetMasking()` and verifies via count.
- `search_photos` `rules` (v3.0): advanced criteria reuse the smart-collection rule validation; rules intersect with the simplified filters. NOTE: searchDesc values are STRINGS after conversion — `spec_helper`'s `photoMatches` tonumbers rating comparisons, and real `findPhotos` parses them server-side (Lightroom's job).
- `LIGHTROOM_MCP_TOOLS` (v3.0): server-side tool filter (`list-tools-handler.ts`) for token-constrained clients; unknown names warn on stderr, no-match falls back to the full set. The DeepSeek harness (`examples/deepseek-harness/`) implements the MCP stdio protocol BY HAND (no SDK dependency) and maps tools to DeepSeek function calling — keep it dependency-free.
- `scripts/run_lua_specs.py` (repo root) reproduces busted behavior over lupa for environments without a Lua install; real CI runs `mise run lua:test`.
- Dust detection (`skills/photo-edit-advisor/`): measured against LrC 15.4, see `reference/dust-attribution.md` before changing thresholds. Three findings that are easy to re-break: (1) the noise scale MUST be measured inside the smooth+bright gate — measuring it globally puts the threshold ~5x above the signal and the detector finds nothing; (2) the gate measures FINE-SCALE detail energy, not plain local standard deviation, because a well-marked spot raises its own local std and gates itself out, leaving a ring the detector then reports as several spots; (3) `FilterList` region boxes are processing tiles, NOT dust coordinates — in a measured case the edit sat at 10% of the width of a 1314px box — and coordinates are not comparable across lenses because the per-lens distortion profile shifts a fixed spot radially by up to 0.024 of frame width.

## Architecture (read before changing transport)

Plugin opens **two LrSocket binds** as servers; MCP server connects to both.

- Plugin :58763 (default) in `mode='receive'` — server writes line-delimited JSON requests
- Plugin :58764 (default) in `mode='send'` — server reads line-delimited JSON responses
- Frame: `\n` terminator on every message (LrSocket buffers until newline)
- Plugin allows **one client per port at a time**. MCP server holds a persistent connection.
- `LrSocket.bind` in `mode='receive'` has a 10s no-client timeout that fires `onError`. Plugin auto-calls `:reconnect()` from a monitor loop in response. Reconnect storms are prevented by setting flags in callbacks and acting on them in the loop (never `:reconnect()` synchronously from `onError`).
- `onMessage` runs in non-yielding context — handler dispatch must be wrapped in `LrTasks.startAsyncTask` so `catalog:withReadAccessDo` can yield.
- Catalog queries that yield (`getTargetPhotos`, `findPhotos`) must run **outside** `withReadAccessDo`. Nesting a yielding query inside the read gate deadlocks on Windows: the task yields to the UI thread holding the gate, never returns, never releases it, wedging the bridge until the server timeout (#124/#134). Only non-yielding per-photo metadata reads belong inside the gate. `getAllPhotos` is a non-yielding enumeration, safe either side. Specs guard this via `getQueriedInsideReadAccess()` in `spec_helper`.

Pattern verified against MIDI2LR (`rsjaffe/MIDI2LR`, see `src/plugin/Client.lua`) — same dual-port LrSocket model, ports 58763/58764 also chosen there.

## Plugin install (manual, no automation)

Copy `plugin/LightroomMCP.lrplugin/` to:
- macOS: `~/Library/Application Support/Adobe/Lightroom/Plugins/`
- Windows: `%APPDATA%\Adobe\Lightroom\Plugins\`

Bundle is pure Lua — same content ships in both `LightroomMCP-macos.lrplugin.zip` and `LightroomMCP-windows.lrplugin.zip` release artifacts. Split is for download UX, not platform code.

Click **Start Server** in Plug-in Manager. Logs at `~/Documents/LrClassicLogs/LightroomMCP.log`.

**Reload behaviour**: "Reload Plug-in" cancels the old task's `LrFunctionContext` (freeing its LrSocket ports) and starts fresh. PluginInit sleeps 0.5 s before binding so the context cancel can flush. Server is ready in ~1 s.

But a reload does NOT guarantee a single live instance, and two hard-won consequences follow (both measured, both now fixed — do not regress them):

1. **A fresh module instance does not replace the old one.** Lightroom re-runs the module while the previous instance's LrSocket callbacks keep serving, so the OLD code and the OLD `pluginState.token` stay live. **Practical consequence for anyone editing Lua: "Reload Plug-in" does NOT put your changes into service.** Measured 17-09: a handler was edited, copied into `%APPDATA%\Adobe\Lightroom\Modules\LightroomMCP.lrplugin\` (which is where Lightroom loads from — NOT the repo), the plugin reloaded, and the dispatcher still answered with the old code's response shape and reproduced the old bug. Verify which code is live by checking a field only the new version emits, and restart Lightroom — not reload — before concluding a fix does not work. The new instance publishes a different token to the file, which is what the bridge sends, and every request then fails `Auth failed (token mismatch)` — dropped silently, so the caller sees only a timeout. `isValidToken` therefore accepts the token published on disk as well as the in-memory one.
2. **Two server tasks can run at once, and no guard on `_G` can stop it.** `resetForReload` signals a survivor only through `running = false`, and `startServer` sets it back to true before a sleeping loop ever observes it. Both loops then share `pluginState.responseGen` — which each start resets to 0 — and invalidate each other's listener on every rebind (`gen=10` and `gen=2` rebinding the same port in the same second), so every `sendResponse` stalls. The monitor loop checks `pluginState.instanceId == instanceId` (monotonic, never reset) and a superseded loop exits — but **that only settles races inside ONE Lua state**. Lightroom runs the plugin in several: one launch logged `PluginInfoProvider loaded` 27 times, and each state has its own `_G`, so two instances could each believe they were alone. The cross-state guard is `ServerLease.lua`, a lease on the filesystem — same design as the bridge's `instance-lock.ts`. Measured on a clean launch: one `Starting LrSocket servers` and 16 `standing down`, where three servers used to fight over the port.

   **Do not "hand the port back" in the server task's cleanup handler.** Releasing the lease on teardown looks tidy and cascades: Lightroom discards short-lived states, and when one of them held the lease an immediate release let a watcher take over within five seconds — onto another state that also died. Six servers in ninety seconds. Letting the lease go stale instead costs one quiet 15s window and turns that into a single calm takeover. Only an explicit `shutdown()` releases.

Note that auto-start plus a manual **Start Server** is two starts; the guards above make that harmless rather than preventing it.

## Conventions

- TS strict mode on. ESM imports must include `.js` extension (NodeNext).
- New Lua handlers: add file under `plugin/LightroomMCP.lrplugin/Handler*.lua`, register in `DISPATCH` table in `PluginInfoProvider.lua`, declare any new LR globals in `lightroom.yml`.
- New MCP tool: add contract in `server/src/tool-contracts.ts` **and** add a `DISPATCH` entry in `PluginInfoProvider.lua`.
- Default ports `58763` (request) / `58764` (response). Server overrides via env vars `LIGHTROOM_MCP_REQUEST_PORT` / `LIGHTROOM_MCP_RESPONSE_PORT` (parsed in `server/src/ports.ts`); plugin overrides via Plug-in Manager fields stored in `LrPrefs` (`requestPort` / `responsePort`). Both sides must agree — change in lockstep.
- Single-bridge instance lock (`server/src/instance-lock.ts`): async by design, self-healing in three layers. (1) Dead-pid locks AND locks whose file stopped being refreshed (≥ 60 s stale — every build ≤ 3.1.2-1 never refreshed) are stolen immediately; live v3.1.2 holders refresh the file's mtime every 5 s and exit when the pid inside stops being theirs. (2) A contender that has waited 5 s writes a `.yield-request` sidecar; a holder whose client is idle (never called a tool, or silent ≥ 10 min — `ClientActivityTracker` in `server/src/client-activity.ts`, env `LIGHTROOM_MCP_IDLE_YIELD_MS` / `LIGHTROOM_MCP_PROBE_YIELD_MS`) yields and exits 0. Do not remove the refresh or the yield protocol without replacing this protection: Claude Desktop's probe/respawn cycle abandons processes with open stdin pipes, and this is the only exit path they have.
- Anti-probe watchdog (`server/src/index.ts`): a fresh bridge with no completed MCP handshake after 5 s (`LIGHTROOM_MCP_HANDSHAKE_TIMEOUT_MS`, `0` disables) self-exits — `StdioServerTransport` does not watch stdin EOF, so a client that abandons a spawned process would otherwise leave a zombie holding the lock. Do not remove the watchdog without replacing this protection; the handshake flag flips in `server.oninitialized`.
- Plugin-gone backstop (`server/src/index.ts`): once both plugin sockets have connected, being down continuously for 10 min (`LIGHTROOM_MCP_PLUGIN_DOWN_EXIT_MS`, `0` disables) self-exits the bridge so a dead Lightroom cannot leave a useless lock holder behind. A bridge that never connected keeps retrying — starting Claude before Lightroom is legitimate. Shutdown-path diagnostics use `fs.writeSync(2, ...)` (`logSync`): `console.error` right before `process.exit` can truncate in Windows pipes.
